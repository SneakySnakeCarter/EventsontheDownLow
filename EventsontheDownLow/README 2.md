# EventsontheDownLow (SQLite + BackgroundTasks + Recurring Events)

This is a source drop, not a ready-made `.xcodeproj` — Xcode project files are
binary/plist bundles that are best generated by Xcode itself. Follow the
steps below (~5 minutes) to get this running.

## 1. Create the Xcode project

1. Xcode → File → New → Project → **iOS → App**
2. Product Name: `EventsontheDownLow`
3. Interface: **SwiftUI**, Language: **Swift**
4. Uncheck "Use Core Data" and "Include Tests" (not needed, though tests are fine to add)
5. Save it anywhere.

## 2. Add these files

Delete the default `ContentView.swift` and the `@main` App file Xcode
generated, then drag the folders from this drop (`Models/`, `Database/`,
`Recurrence/`, `Services/`, `ViewModels/`, `Views/`, and
`EventsontheDownLowApp.swift`) into the Xcode project navigator.
✅ Check "Copy items if needed" and add them to the `EventsontheDownLow` target.

## Photo attachments — no extra Info.plist entry needed

Event photos are picked via SwiftUI's `PhotosPicker` (from the `PhotosUI`
framework), which runs the system photo picker out-of-process. Unlike the
older `UIImagePickerController`/`PHPickerViewController` full-library-access
APIs, this does **not** require an `NSPhotoLibraryUsageDescription` key or
any permission prompt — the app only ever receives the specific photo(s) the
user explicitly picks, never library access. Nothing to add here.

## 3. Link SQLite

Target → **Build Phases** → **Link Binary With Libraries** → **+** →
add `libsqlite3.tbd` (search "sqlite"). This gives you the `SQLite3` module
used in `SQLiteDatabase.swift` — no SPM package required.

## 4. Enable Background Modes

Target → **Signing & Capabilities** → **+ Capability** → **Background Modes**
→ check:
- ✅ Background fetch
- ✅ Background processing

## 5. Info.plist additions

Add this array so iOS allows your app to register the task identifiers:

```xml
<key>BGTaskSchedulerPermittedIdentifiers</key>
<array>
    <string>com.eventsonthedownlow.refresh</string>
    <string>com.eventsonthedownlow.processing</string>
</array>
```

Also add a usage description if you later add EventKit import/export:
```xml
<key>NSUserNotificationsUsageDescription</key>
<string>EventsontheDownLow sends reminders for your upcoming events.</string>
```
(Local notifications don't strictly require an Info.plist string, but
`UNUserNotificationCenter.requestAuthorization` will show the system prompt
automatically the first time the app runs.)

### Camera capture (Take Photo in event editor)

Unlike `PhotosPicker` (which needs no permission string at all), the camera
capture feature uses `UIImagePickerController`, which **does** require a
usage description — the app will crash on launch of the camera without it:

```xml
<key>NSCameraUsageDescription</key>
<string>EventsontheDownLow uses the camera to attach a photo to an event.</string>
```

### Save to Photos

The "Save to Photos" button writes a copy to the system Photos library using
**add-only** access — a narrower permission than full library read access,
meaning the app can add photos but never browse or read existing ones:

```xml
<key>NSPhotoLibraryAddUsageDescription</key>
<string>EventsontheDownLow can save event photos to your Photos library when you choose to.</string>
```

## 6. Run it

Build & run. You should see an empty "Events" list with a **+** button.
Add a recurring event (e.g. Weekly, every 1 week, Mon/Wed/Fri) and you'll
see it expand into individual occurrences in the list for the next 60 days.

## How recurrence works

- `RecurrenceRule` is a simplified RFC5545-style rule (`FREQ`, `INTERVAL`,
  `BYDAY`, `COUNT`, `UNTIL`) stored as a single semicolon-delimited string in
  the `recurrence_rule` TEXT column — no need for a second SQL table.
- `RecurrenceEngine.occurrences(for:in:_:)` expands a stored `CalendarEvent`
  into concrete `EventOccurrence`s within any date window, lazily. Nothing is
  pre-materialized in the database — this keeps edits/deletes simple (you
  only ever touch the one base row) at the cost of recomputing expansion on
  each read, which is cheap for typical calendar volumes.

## How reminders work

- Each event has a fully user-configurable list of reminders
  (`CalendarEvent.reminderOffsets` — minutes before start; `0` means "at
  start time"). Add as many as you want, at any interval, from the
  Reminders section in the event editor. New events default to a single
  "at start time" reminder.
- `NotificationScheduler` builds every (occurrence × reminder) candidate
  across *all* events, sorts them by fire time, and schedules only the
  soonest **60** — leaving headroom under iOS's actual 64-pending-local-
  notification cap. There's no separate "refill" bookkeeping: the next
  scheduling pass (app open, or the periodic background refresh task)
  just recomputes the whole candidate pool fresh and naturally pulls in
  whatever's now soonest, so a never-ending daily reminder keeps getting
  topped up over time without ever exceeding the cap.
- Both `EventListViewModel` and `BackgroundTaskManager` feed the scheduler
  from a **~2-year-wide** candidate window (not just what's on-screen),
  specifically so there's always a deep enough pool for that count-based
  cap to draw "the next 60" from.

## How the background tasks work

- **`com.eventsonthedownlow.refresh`** (`BGAppRefreshTask`): runs periodically
  (system-decided timing, requested ~hourly), expands events across the
  wide ~2-year lookahead described above and hands them to
  `NotificationScheduler`, which does the actual capping/scheduling.
- **`com.eventsonthedownlow.processing`** (`BGProcessingTask`): runs roughly
  daily, prunes events (and finished recurring series) older than a year,
  and cleans up any orphaned photo files on disk (see `EventImageStore.
  deleteOrphanedFiles` — catches photos picked/taken during an editing
  session that was cancelled before saving).
- Both are re-scheduled every time they run, and every time the app enters
  the background (`scenePhase == .background`), since BGTaskScheduler
  requests are one-shot.

### Testing background tasks in the simulator/device

Pause at a breakpoint after `BGTaskScheduler.shared.submit(...)` runs, then
in the LLDB console:
```
e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.eventsonthedownlow.refresh"]
```
(swap in `com.eventsonthedownlow.processing` for the other task). This forces
iOS to run the handler immediately instead of waiting for real background time.

## Pull-down help drawer

`HelpDrawer.swift` is a reusable component — a small handle (line + chevron)
sits just below the nav title; dragging it down (or tapping it) reveals
page-specific help content, up to 75% of the screen height, with the same
gesture closing it again. Currently used on both the Events list and the
event editor. Content shown comes from `HELP_DOCUMENTATION_PLAN.md`'s
per-feature outline.

**Important layout gotcha if you add this to another screen:** `HelpDrawer`
needs a `GeometryReader` to compute its 75%-height, but a `GeometryReader`
placed as `NavigationStack`'s *direct* child breaks the nav bar entirely
(title and toolbar buttons silently fail to render — this bit us during
development). The fix is to attach it via `.overlay(alignment: .top)` on
the `List`/`Form` instead of wrapping it:
```swift
List { ... }
    .safeAreaInset(edge: .top, spacing: 0) {
        Color.clear.frame(height: HelpDrawerMetrics.handleHeight)
    }
    .overlay(alignment: .top) {
        GeometryReader { geo in
            HelpDrawer(availableHeight: geo.size.height) { /* page content */ }
        }
    }
```
The `.safeAreaInset` reserves space so the closed handle doesn't cover your
first row/field; the `.overlay` keeps `GeometryReader` out of
`NavigationStack`'s direct child position.

## Larger expanded photo in notifications

By default, iOS shows event photos at a modest size when a notification is
expanded — that sizing is OS-controlled and can't be enlarged through the
plain attachment API. To get a full-width expanded image instead, this drop
includes an optional **Notification Content Extension** (a separate Xcode
target) under `NotificationContentExtension/`. See
`NotificationContentExtension/SETUP.md` for the full walkthrough — it's a
bit more involved than adding files to your existing target since it
requires creating a new extension target in Xcode.

## Extending this

- **iCloud sync**: swap `SQLiteDatabase` for `SQLite.swift` + a CloudKit
  mirror, or run the raw sqlite3 file through a sync layer of your choice.
- **EventKit interop**: if you also want events to show in the native
  Calendar app, you'd additionally save an `EKEvent` — ask if you'd like that
  bridging code added.
- **Exceptions to a recurring event** (e.g. "this one Tuesday is cancelled"):
  add an `exception_dates` TEXT column (comma-separated epoch list) to
  `events` and have `RecurrenceEngine` skip any candidate date present there.
